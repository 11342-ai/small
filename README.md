# PDF 处理功能的价值分析（STAR 复盘）

> 本文回答：PDF 功能几个方面存在的理由是否站得住脚。结构采用 STAR 法则（Situation 背景 / Task 任务 / Action 行动 / Result 结果）。
> 结论先行：站得住，但有边界——优势集中在"大文档、重复使用、要沉淀为资产的场景"；一次性小文档手动复制粘贴更省。

## S 背景（Situation）

使用场景：用户手头有 PDF 文档（法律文书、论文、报告、判决书等），希望 agent 读进来、提取内容、整理成规范 markdown。此前这类工作靠人手动打开 PDF、复制粘贴、再手工排版——粘贴进对话的文本带着分页符、页码、水印、逐字拆分（"第 一 百 四 十 一 条"）、换行粘连等噪声，既浪费 token 又难读。

项目定位：本地单机个人 agent（DeepSeek 对话 + 工具 + 会话 + 长期记忆 + 知识库）。核心原则：零依赖优先、依赖单向、安全护栏（Pass/Ask 权限）、文档先行。PDF 功能是"外部文档变成可对话、可沉淀资产"的入口。

## T 任务（Task）

把"PDF → 干净 markdown"做成稳定链路，要解决四件事：

- 解析：PDF 格式复杂（字体、版式、扫描件、双栏），自己写解析器不现实。
- 清洗：解析产物噪声多。规则能修的归规则，语义问题（段落合并、词间距、双栏重排）要 AI。
- 成本：大文档 token 和工具轮次都贵，要窗口化、缓存、分片。
- 稳定：流程要固化（解析→清洗→细读→整理→落盘→汇报），不靠每次临场发挥。

## A 行动（Action）

- 引擎选型：不自研解析器，选 lit（LlamaIndex LiteParse，Node CLI，npm 包 @llamaindex/liteparse，即所说的"tle 库"）。本地免费、一个 npm 包、支持 PDF/DOCX/PPTX/XLSX/图片（Office 走 LibreOffice，图片/扫描件走 OCR）。
- 封装三个内置工具：doc_parse（解析落盘）、doc_read（窗口化读缓存产物）、doc_clean（确定性清洗）。agent 不记 lit 命令，只调固定参数模板的工具。
- 缓存复用：产物落 ~/.small/cache，按源路径 sha256 命名，同源同内容重复解析直接命中（parse once），降低重复劳动。
- 规则与 AI 分工：规则处理分页符行、页码行、横线页码残留（－70－）、行内水印重复、相邻重复行、空行折叠、CJK 字间空格压缩；段落合并、词间距恢复、换行粘连、列表错位、数字空格、双栏重排交给 AI 整理阶段。
- 流程固化：workflow pdf 分支（frontmatter + 步骤正文，embed 注入提示词）+ /pdf 命令双通道进入；六步执行、停止条件明确（产出汇报后等待确认；工具失败、轮次超限、用户打断即停）。
- 成本控制：doc_read 窗口化、解析返回 40 行摘要先判相关性、大 PDF 按 pages 分片（每片约 50 页独立缓存）、max_tool_rounds 可配置（缺省 20）。

## R 结果（Result）

对照五个疑问逐条回答。

### R1 相比手动复制粘贴，是否有优势？

有，但分场景。

- 大文档/重复使用：几百页的刑法、裁判文书，手动粘贴不可行（一次贴不完、噪声重、格式乱）。链路全自动，一次指令完成解析+清洗+整理+落盘，且整理产物是规范 markdown（对照样例见 Zoo/pdf工具对比效果/ 的原版 vs 经过 agent 处理）。
- 资产沉淀：整理后的 markdown 可以进知识库/记忆，成为可检索资产；手动粘贴是"用完即弃"。
- 小文档/一次性：手动复制粘贴更快（无依赖、无 token 成本），链路反而繁琐。这是边界。

### R2 相比裸 lit（被封装的原库），是否有优势？

有。lit 只做"解析成文本"，输出带噪声（分页符、页码、水印、逐字拆分），且没有流程、没有缓存、没有语义整理。本项目在 lit 之上加了：

- doc_clean 确定性清洗（规则是原库没有的）。
- AI 整理（段落合并/词间距/双栏重排，原库给不了语义层）。
- 缓存命中（重复解析不调 lit）。
- 工作流固化（步骤、停止条件、落盘确认）。

代价：多一层封装 + 整理阶段的 token 消耗。若只需"把 PDF 转成文本"，裸 lit 更省；本项目卖的是"从 PDF 到可用的文档资产"的完整链路。

### R3 token 消耗是否会抵消优势？
不会抵消，但要承认成本存在。

- 成本构成：解析（返回摘要，小）、细读（窗口化，可控）、整理（读全文 + 输出，大头）、落盘（输出，中等）。
- 对比基准：手动把粘贴的噪声文本灌给模型，读同样内容同样花 token，且噪声文本 token 更多、理解更差、还需要用户自己重新整理排版。链路的 token 不是白花的。
- 控制手段：窗口读、摘要先判相关性、pages 分片、缓存（重复解析零成本）、整理产物落盘后再次使用只读产物（不再解析）。
- 结论：一次性小文档，手动复制粘贴 token 上更优；大文档、重复使用、要沉淀资产时，链路的 token 成本换来的是质量和资产，划算。

### R4 相比市面上的软件（预设脚本），是否有足够优势？

要看对标对象。

- 传统工具（pdftotext、PDF 阅读器导出、格式整理小工具）：固定规则、无语义理解。双栏空白、逐字拆分、水印、段落乱序这类"需要理解语义才能修"的问题，脚本修不了，必须人工。
- 通用 AI 问答服务（ChatPDF 类）：云端、按次问答、不落本地资产，且无法把整理结果写进你的知识库/记忆体系。
- 本项目优势：本地（数据不出本机）、"解析+清洗+AI 整理+落盘+沉淀"一条龙、产物进知识库可复用、与对话/记忆/知识库生态打通。
- 劣势：依赖 lit 安装、整理消耗对话 token、复杂版式（表格/公式/扫描件）效果不如专业解析服务（见 R5）。

### R5 其他 PDF 解析方法对比，我们的优劣势

- 纯规则引擎（pdftotext / pdfminer / pymupdf / pdfplumber）：快、免费、本地；但复杂版式要靠大量脚本调参，中文逐字拆分/水印/双栏要后处理，每种文档调一次，维护成本高。本项目把"规则清洗"做成通用 doc_clean，避免了重复调参，但语义层仍留给 AI。
- OCR（tesseract / PaddleOCR）：能处理扫描件/图片；但慢、有识别错误、中文准确率依赖模型。本项目扫描件也走 lit 的 OCR 路径，效果受底层引擎限制——扫描件场景不是强项。
- 大模型直读（多模态模型直接看页面，或把全文灌给模型）：语义理解最强，直接问答；但 token 巨大、超长文档超上下文、不能落成结构化资产、云端有数据风险。本项目用"分片 + 窗口读 + 整理后落盘"规避了整灌，代价是丢"直接看版式"的能力（表格/公式位置信息）。
- 专业 AI 解析服务/库（LlamaParse / MinerU / Marker / Mathpix）：版式理解最强（表格/公式/双栏/标题层级），但多数是云端付费、闭源、数据出境；本地版（MinerU/Marker）要下载大模型、配置重。本项目本地轻量（一个 npm 包 + 已有对话模型），复杂版式确实不如它们——这是明知的取舍。
- 我们的优势：本地零配置、规则+AI 分工无需额外模型、产物落缓存复用、与记忆/知识库打通形成资产。
- 我们的缺点：复杂版式（表格/公式/扫描件）质量上限低于专业解析服务；语义整理消耗对话 token；依赖 lit 外部命令（需安装）。

## 结论

PDF 功能的理由站得住，但定位要清楚：它是"本地、轻量、资产导向"的文档入口，不是"最强解析器"。对标场景——大文档、中文文书/论文、重复使用、要沉淀知识资产的场景下优势成立；一次性小文档、复杂版式（扫描表格/公式）场景下不如手动或专业工具。

## 附：我对项目的理解

（基于代码与设计文档的复述，2026-09-02）

定位：本地单机个人 agent，自建规范（与通用 Go 风格不同处已在 CLAUDE.md 标注），核心原则是依赖单向、解耦到隔离点、功能需求决定形态。

技术选型的几条主线：

- 零依赖优先：存储全用文件（session JSONL、memory Markdown + bigram 索引、kb 解析产物、cache 目录），唯一破例是 kb 的 goldmark；不上 SQLite、不上向量库，量级不够就是不做。
- 最小可运行 + 逐步叠加：路线图分梯队，每个模块"文档先行 → 最小实现 → 节点提交"，不超前设计（明确不做的清单很清晰）。
- 安全护栏是横切层：命令与工具统一 Pass/Ask 权限，写工具必须登记权限表，Ask 无确认即拒绝（fail-closed）。
- 提示词资产化：人格、工作流都用 go:embed 的 md（frontmatter + 正文），组合根装配，不改循环代码。
- 传输层收敛：adapter.go 是全项目唯一 import provider 的 agent 文件，翻译 Turn↔Message，provider 不感知业务。

开发风格：

- 文档先行，Zoo/model 每模块一份设计文档 + 决策记录，用户拍板才实现。
- 一工具一构造函数、执行逻辑外置具名函数可单测；编译期断言锁接口；合并门槛 go test -race / go vet / gofmt 全绿。
- 边界防御只在系统边界（HTTP、外部输入），内部契约信任不重复防御。

PDF 功能在这个框架里的位置：它是"外部文档进对话/资产"的入口，做法完全符合项目风格——不重复造轮子（借 lit 做引擎），把轮子嵌进自己的体系（工具化 + 规则/AI 分工 + 缓存 + 流程固化 + 权限登记），代价与边界是明知的取舍（见 R3/R5）。
