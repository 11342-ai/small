# Tool 模块设计文档

> 位置：`internal/tool`
> 状态：**阶段一（tool 模块本体）+ 阶段二（provider DTO 扩展 + agent 工具循环适配）均已实现**，通过单测（含 `-race`）与 `go vet`、`gofmt`、`go build`。
> 关联：`agent.md` 已知扩展点"工具调用循环"；`provider.md` 传输层扩展点"完整工具调用字段"。

## 1. 定位与职责

tool 模块承载"给模型使用的工具"这一能力的三要素：**声明、执行、注册**。它属于领域层，负责工具契约与本地执行，不感知任何传输层细节。

依赖方向（拟）：
```
main(组合根) → agent → tool
                  ↘ provider → config
```

- agent 消费 tool（工具循环、结果回灌）；main 在组合根把具体工具注册进 Registry 后整体注入 agent。
- **tool 与 provider 互不感知**；两者之间的翻译继续收敛在 agent 包的 adapter（复刻现有"唯一 import provider 的文件"隔离点模式）。
- 不产生任何反向或循环依赖。

## 2. 三个核心抽象

### 2.1 声明（Spec）—— 模型看到的契约

- 内容：**名称、描述、参数说明** 三件套。
- 性质：静态、可序列化、无副作用；装配期固定，模型上下文里的 token 也主要消耗在它身上。
- **参数说明统一采用 JSON Schema**：OpenAI（parameters）、Claude（input_schema）、MCP（inputSchema）等各家的底层标准都是它，跨提供商通用。未来换后端时 provider 层 DTO 直接映射即可，tool 层零改动。

### 2.2 执行（Execute）—— 本地的动作

- 内容：给定参数执行动作，返回结果。
- 性质：动态、可能有副作用（网络 / 文件 / 命令）。
- 参数形态：以"模型返回的原始 JSON"整体传入，由各工具自行解码为自身需要的强类型。判据：参数来源天然就是 JSON 字符串，逐个工具做运行时校验或泛型化引入的复杂度大于收益。
- 结果形态：文本（JSON 或纯文本）回灌模型；附"是否业务失败"标记，见 3.4。

### 2.3 注册表（Registry）—— 模块对象

- 内容：**名称 → 工具** 的映射容器，通过 `New()` 创建（与 `config.Load` / `provider.New` / `agent.New` 的构造风格一致），是组合根与 agent 循环拿到的"模块对象"。
- 能力：注册（重名报错）、**批量注册（`RegisterAll`，遇错即止）**、按名查找、列出全部（**顺序稳定**，供序列化成 tools 数组）。
- 并发：当前组合根一次性装配、循环期只读，不加并发锁；以注释约定"注册只发生在启动期"。若未来出现动态注册（如运行时接 MCP 工具），再补锁。

## 3. 边界划分（四条约定）

### 3.1 声明与执行分离

- 判据：**给谁用 + 生命周期不同**。
- Spec 给模型与序列化层，装配期固定；Execute 给运行环境，每轮循环都可能发生。混在一起会让"只想拿工具列表做序列化"的代码被迫持有可执行实例。

### 3.2 tool 与 provider 互不感知
- 判据：复刻 agent 包"只有 adapter.go import provider"的隔离点模式。
- provider 的 DTO 只增加 tools 字段与消息中的工具调用记录（纯传输数据）；`Spec ↔ 传输层工具声明`、`传输层工具调用 ↔ agent 调用记录` 的翻译只发生在 adapter。
- 效果：换后端时 tool 模块与内置工具一行不改。

### 3.3 装配期与运行期分离

- 判据：注册是**装配动作**（组合根一次性调用），查询/执行是**业务动作**（循环热调用）。
- 与"`config.Load` 只读一次环境变量、随后整体注入"同理，两个阶段不在同一层出现。

### 3.4 业务失败 vs 框架错误
- 约定：
  - 工具自己返回的**业务失败**（如 API 404、文件不存在）作为"结果"正常返回，附失败标记，由模型自行决定重试或换策略；
  - 工具的**框架级错误**（panic、配置错误、契约破坏）才向上抛错误并中止整个循环。
- 判据：业务失败对模型只是一条可观察输入，当错误处理会杀掉整个 agent 循环；这也是 MCP / OpenAI 的通行约定。
- 依据现有"只在系统边界防御、信任内部契约"的原则：工具内部不重复防御，但参数解码失败等系统边界要处理。

## 4. 接口与结构拆分原则

### 4.1 数据用结构体，能力用接口

| 抽象 | 形态 | 依据 |
|---|---|---|
| Spec / 结果 / 调用记录 | 结构体 | 纯数据、需序列化、可扩展字段 |
| 工具能力 | 接口（声明 + 执行） | 实现多样（内置 / 未来 MCP 适配器 / 测试桩），需多态替换 |
| 工具集合（Registry） | 具体结构体 | 唯一容器，无第二实现（见 4.2） |

### 4.2 "Registry 不接口化"的完整解释

"不接口化"指的是：**除了工具能力接口之外，不再为"工具集合"这个容器再造一层抽象接口**（例如"工具仓库"），让 agent 直接依赖 Registry 这个具体结构体。

需要先区分"接口"出现的两个层级：

1. **工具能力接口**——声明 Spec 与 Execute。**这一层必须保留**：工具实现是多样的（内置工具、未来 MCP 适配器、测试桩），需要靠接口承载多态，替换实现不动循环代码。
2. **容器抽象**——即"要不要把 Registry 也包成接口，让 agent 依赖接口而不是具体结构体"。

"不接口化"只针对第 2 层：不做。理由：

- 接口的价值在于"存在多种实现需要替换"。工具有多实现 → 第 1 层接口必要；Registry 是唯一的具体容器，没有第二种实现需要替换 → 第 2 层接口不承载任何真实差异，是空抽象，只会增加一层间接。
- 测试不需要 mock 容器：工具循环的测试往**真实 Registry** 里注册几个测试桩工具即可，多态发生在工具层而非容器层；桩工具实现第 1 层接口即可。
- 项目先例一致：provider 的 Completer 接口化，是因为存在"支持流式 / 不支持流式"的能力差异需要运行时探测；而 retry 的策略、config 的配置都是具体结构体——**单一实现的东西不造接口**。
- 注意：**不接口化 ≠ 不用接口**。Registry 内部仍然以工具能力接口持有每一个工具；这只是说 Registry 自身不再被二次抽象。

### 4.3 三个判断点

1. **声明为何聚合为一个整体**，而非拆成"取名字 / 取描述 / 取参数"三个取值方法：三件套永远一起被序列化（进 tools 数组就是一次打包），聚合保整体性；且结构体能扩展字段而接口签名不变。
2. **参数为何用原始 JSON 而非泛型化**：参数来源是模型吐出的 JSON 字符串，泛型化要付出 schema 生成与编解码成本，收益不成比例。
3. **接口定义在谁那里**：工具能力接口由 tool 包导出（能力契约的中立拥有者，实现方与消费方都依赖它，类似标准库 Handler 的模式）；Registry 以具体类型注入 agent。

## 5. 行业实践对比

### 5.1 OpenAI Codex CLI

- **手段**：三层分离。工具声明（JSON Schema）独立成 crate；core 内注册表把"工具名 → 执行器"映射起来统一路由；各执行器（shell / 打补丁 / MCP 客户端 / 目录列举）各自实现；沙箱与审批作为执行管线环绕在工具外面，工具本身不写守卫代码。
- **优点**：大规模下边界清晰、工具可独立测试、路由集中；声明层用代码生成保证 schema 与结构一致。
- **缺点**：对小程序是重装备——多级运行时、schema 代码生成、核心模块体量巨大，认知成本高。

### 5.2 Anthropic Claude + MCP

- **手段**：① JSON Schema 通用契约（各家方言差异用适配器抹平）；② MCP 把工具变成**独立进程的 JSON-RPC 服务**（列工具 / 调用工具两个标准方法），宿主不写工具代码、工具不知道模型是谁——目前最彻底的解耦；③ 失败标记语义：业务失败作为结果回灌，不终止循环。
- **关键边界认知**：MCP 只规定"宿主 ↔ 服务器"的通信，不规定"宿主 ↔ 模型"；模型那侧仍走各家 tool use API，协议层独立。
- **优点**：跨语言跨生态最大解耦，工具可独立部署演进，写一次多模型可用。
- **缺点**：进程边界有开销、调试链路长、协议学习成本——解耦度是用运行时复杂度换的。

### 5.3 DeepSeek Harness（dsh）

- **手段**：一切皆插件。插件微内核只负责加载 / 依赖 / 清理；模型适配器、工具注册表、会话日志、**甚至 agent 循环本身**都是可替换插件。工具执行走"前置钩子 → 工具本体 → 后置钩子"管道，审批 / 沙箱 / 超时 / 重试 / 结果改写统一挂在管道上，工具作者不重复写守卫；会话日志作为运行时不变量，可逐帧回放调试。
- **优点**：横切关注点与工具本体彻底分离；动态加载 / 替换；可观测性好。
- **缺点**：体量巨大（数十万行、数百个包），"没有特权核心"的代价是没有简单的默认路径，个人 / 小项目消化不了。

### 5.4 OpenClaw

- **手段**：工具目录集中注册 + **多层策略管道**（按 profile / 提供商 / agent 类型 / 群聊场景 / 沙箱 / 子 agent 逐层过滤暴露给模型的工具集）；工具按类别分组；内置 MCP 客户端把外部工具归一成本地同一形态。
- **优点**：场景化暴露——不同场景只给模型当时需要的工具，省 token 且降低误用率。
- **缺点**：策略管道本身就是一个规则引擎，工具数量小于两位数时是纯负担。

### 5.5 共性收敛（五条）

1. **声明与执行分离**——四家一致，最大公约数。
2. **JSON Schema 作参数契约**——无替代品。
3. **注册表集中路由**——名字到实现的映射，外加按场景裁剪暴露面。
4. **策略管线（中间件）**——审批 / 沙箱 / 超时 / 重试 / 日志是横切关注点，不进工具本体。
5. **结果规范化 + 失败标记**——业务失败是数据，框架错误才中止。

## 6. 针对本项目规模的取舍

项目特征：单二进制 CLI、三个包、组合根一次性装配、翻译收敛在 adapter。对照上表：

| 行业做法 | 本项目取舍 | 理由 |
|---|---|---|
| 声明 / 执行分离 | ✅ 吸收 | 零成本收益最大 |
| JSON Schema 参数契约 | ✅ 吸收 | 零成本兼容换后端 |
| 注册表路由 | ✅ 吸收（不接口化） | 薄容器够用，见 4.2 |
| 失败标记语义 | ✅ 吸收 | 一行字段，语义清晰 |
| 插件内核（Cordis） | ❌ 砍掉 | 为"运行时热替换"服务；组合根装配 + 选项模式已覆盖需求 |
| MCP 进程边界 | ❌ 砍掉 | 单进程内是纯负担；将来要接外部工具时在 Registry 下加一个 MCP 适配器即可，工具能力接口不变 |
| 多层策略管道 | ❌ 砍掉 | 工具个位数规模用不上；真需要时退化为注册表上一个可选钩子 |
| 沙箱 | ❌ 砍掉 | 无此需求 |

## 7. 落地路径

**阶段一（本模块，不碰 agent）**：`internal/tool` 三件套（声明 / 执行 / 注册表）+ 极简内置示例工具 + 注册表单测（重名报错、未命中、列出顺序稳定）。此阶段可独立合入，不影响现有对话功能。

**阶段二（接入，agent.md 已知扩展点）**：
- 对话消息增加"工具结果"回灌形态（携带对应调用标识）；
- 结果增加"模型请求的调用列表"；
- adapter 负责声明与调用记录的翻译（延续隔离点约定）；
- agent 循环变为：调用 → 若模型请求了工具则执行并回灌 → 再调用，直到不再请求工具。
- 不支持工具的后端沿用现有"探测 + 降级"模式，退化为纯对话。
- **接线形态（结构依赖显式入参）**：`agent.New(chat, reg, opts...)` 收活注册表（执行调用）；adapter `NewProviderChat(client, model, specs, opts...)` 收冻结声明（`reg.List()`，只序列化不执行）；行为开关（thinking 等）走 Option。`tools`/`specs` 传 nil 即退化为纯对话。
- **权责分离（内置清单集中持有）**：内置工具的清单由 `builtin.RegisterBuiltins(reg)` 集中注册（底层走 `Registry.RegisterAll` 批量原语）——新增内置工具只在 builtin 包追加一个元素，组合根（main）不改一行；组合根只调用注册入口，不逐个枚举工具。命名上 `RegisterBuiltins` 与 `Registry.RegisterAll` 区分：前者是"注册全部内置工具"的入口，后者是批量原语。

## 8. 待决问题
