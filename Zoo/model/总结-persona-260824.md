# 会话总结：Persona（人格）模块

> 时间：2026-08-24
> 范围：`internal/persona` 提示词源部件 + `session` 头行 meta（人格绑定）+ `main` 装配（`--persona` flag + 优先级）+ 位置参数防护
> 状态：全部实现完成，`gofmt` / `go vet` / `go test -race` / `go build` 全绿；CLI 冒烟通过
> 关联：`Zoo/model/persona.md`（设计文档）、`Zoo/路线图.md`（已勾选）、`CLAUDE.md`（决策表 + CLI 参数表）、`Zoo/model/memory.md`（叶子对照）

## 1. 本会话解决的问题与边界

### 1.1 问题

1. **系统提示词硬编码**：`main.go` 里拼死的字符串，换风格要改代码重编译。目标是把"人格/风格"变成可命名的、可挑选的模块。
2. **人格切换语义**：原设想"启动时加载人格 / 对话长度为 0 时斜杠指定"，且因"缓存从前面算起"限制只能在长度 0 时换。需要澄清语义与缓存顾虑。
3. **会话绑定与恢复**：一个对话一个人格，恢复会话要自动带出人格（落盘持久化）。

### 1.2 问题边界

| 层 | 职责 | 明确的"不做什么" |
|---|---|---|
| `persona` | 提示词源部件：`go:embed` 内置人格（frontmatter + 正文），`Manager{Get/List/Default}` | 不 import 任何内部包（叶子）；**不被 agent 依赖**（system 是字符串） |
| `session` | 头行 meta `{"meta":{"persona":...}}`：WriteMeta/Meta/Load 跳头/Rewrite 保头 | 不改消息行格式；旧文件（无头行）照常读 |
| `main` | `--persona` flag + 优先级选择 + system 拼装 + 新建会话写头 | 装配逻辑集中在组合根 |
| `agent` | **零改动** | system 是构造期字符串；persist.go 只调 Append |
| `config` | **零改动** | 无新配置项（默认人格 = default.md，改文件即可） |

**明确不做（YAGNI）**：中途切换人格、角色卡格式（开场白/示例对话）、人格组合/继承、运行时目录加载（`SMALL_PERSONA_DIR`）、斜杠命令、旧会话 meta 回填。

## 2. 分歧与结论

### 2.1 缓存顾虑（本会话最大分歧，认知纠偏）

- **分歧**：用户主张"只能在对话长度为 0 时换人格"——理由是"命中缓存是从前面开始算的，一开始就得降低语句开头有大变更的可能"。
- **事实纠正**：① DeepSeek 缓存是**前缀匹配**（system 在最前，是前缀的锚）——这个直觉对；② 但改 system prompt **无论长度是 0 还是 100，当次请求都全前缀 miss**（token 0 起就不同）；③ "长度 0 时改"唯一差别是"没有已建缓存可浪费"，而浪费是一次性、毫秒级、下一轮自动重建。真正的原则是"切换频率"而非"切换时机"。
- **结论**：缓存**不当硬约束**。本项目本地 CLI 单用户、低频、短对话，缓存收益可忽略；"换人格=新起点（清历史防串味）"的论据是**产品语义**而非缓存。
- **决策依据**：优化对象本身不是瓶颈时，不为它牺牲产品灵活性；论据换柱子（语义替代缓存），结论保得住。
- **防回卷**：纠偏记录进 `persona.md §2.1`，防止将来有人用缓存理由回卷设计。

### 2.2 切换语义：一个对话 = 一个人格

- **分歧/澄清**：用户澄清"换风格本质不是中途改，而是**创建对话时固定一个风格**；对话中旬不切（不是技术禁止，是产品不提供）"——等价于硬切换。
- **结论**：persona 在会话创建时定型，存续期内不切换；恢复以会话 meta 为准（flag 不覆盖）。
- **决策依据**：旧人格的 assistant 回复留在历史里会让模型串味（二次元 vs 严谨科学家反差尤甚）。

### 2.3 模块形态：不抽 interface

- **分歧**：用户主张"一个代表 persona 的 struct + 一个 interface 统合"。
- **结论**：第一版**不抽 interface**，具体 `Manager` struct。
- **决策依据**：agent 不消费 persona（只收字符串）、main 不需要多态——接口是空抽象；第二个来源（如运行时目录）出现时在**使用方（main）**抽 `Provider` + 编译期断言（与 session/memory Store 同一惯例）。

### 2.4 存储来源：go:embed vs 运行时目录

- **分歧**：用户提议 `go:embed` 编译期快照（"embed 不好也可以调整"）。
- **结论**：**纯 go:embed**。人格是代码资产（开发者维护），对照 memory 是运行时读**用户可编辑**文件——两者来源性质不同，正好对照。加人格 = 加 `personas/*.md` + 重编译，对内置人格可接受。
- **决策依据**：编译期快照零运行时失败、单二进制分发。

### 2.5 入口：flag 取代斜杠命令

- **分歧**：原设想"启动加载 + `/chatater catton` 长度 0 斜杠指定"两个入口。
- **结论**：只留 `--persona` flag + 默认人格兜底，不做斜杠命令（创建时指定即够；命令解析不进历史是另一摊事，省输入循环改动）。
- **决策依据**：两条路殊途同归，砍重复入口。

### 2.6 实现期修正（非用户分歧）

- **"新建会话"判定**：原设计用"消息条数==0"判定新建。实现发现：创建后未聊过的会话（只有头行）会被误判为新建、flag 覆盖已定型人格。**修正**：以"头行有无"判定——头行存在即已定型（meta 优先），无头行且无消息才是真正的新建（flag 生效并写头行）。
- **角色句归属**：设计文档 §6 示例把"你是一个简洁的助手…"留在 base——那样选别的人格会**继承"简洁"约束**（错误）。**修正**：角色句移入 `default.md`，base 只留工具/记忆契约（人格无关）。

## 3. 踩坑记录（忽视临界情况的代价）

### 3.1 缓存过度推论（认知层踩坑）

- **现象**：从"缓存从前面算起"推导出"只能在长度 0 时换人格"，把一次性的、可忽略的 miss 成本放大成产品约束。
- **根因**：混淆"缓存命中的持续收益（每轮打折）"与"换人格的一次性成本（一次全 miss）"；成本与收益的量级判断失衡。
- **解决**：事实纠正 + 决策记录防回卷（§2.1）。

### 3.2 `-- persona` 空格导致静默降级（CLI 使用层）

- **现象**：用户运行 `go run . -- persona catton`（`--` 与 `persona` 间有空格），程序静默加载了 default 人格。
- **根因**：`--` 是 flag 终止符，`persona catton` 变成位置参数；程序从未检查位置参数，静默忽略。
- **解决**：组合根加位置参数防护——`flag.Args()` 非空即 fail fast，并提示正确写法（`--persona catton`）。错误立刻暴露，不再静默降级。

### 3.3 "只有头行"的会话被误判为新建

- **现象**：创建会话（写了头行）但未聊过就退出，再次进入时被当成新建会话，flag 覆盖了已定型人格。
- **根因**：判定"新建"用的是消息条数（0），而头行本身不产生消息条数。
- **解决**：改为以头行有无判定（见 §2.6），冒烟测试锁住行为。

### 3.4 角色句留在 base 会污染所有人格

- **现象**：若按设计文档 §6 字面实现（base 保留"简洁助手"角色句），选 catton/onee 等人格时也会继承"简洁"约束。
- **根因**：把"角色（persona 职责）"和"契约（base 职责）"混在一段文本里，没有在拆分时明确归属。
- **解决**：角色句归 default.md，base 只留工具/记忆契约。

## 4. 后续开发的统一与连贯性

以下条目为后续开发硬性对齐项（核心已写入 CLAUDE.md）：

1. **persona 是叶子**：`main → persona`；persona 不 import 任何内部包；**agent 不感知 persona**（system 是字符串）——人格是"提示词源"，不是 agent 的协作对象（对照 tool）。
2. **一个对话一个人格**：创建时定型，不中途切；会话头行 `{"meta":{...}}` 绑定，旧文件兼容（无头行照常读），Rewrite 保头（截断不丢人格）。
3. **人格是代码资产**：`go:embed` 编译期快照，加人格 = 加 `personas/*.md` + 重编译；frontmatter 用 yaml.v3（复用 config 依赖，**零新增依赖**）。
4. **决策表记录**：CLAUDE.md 新增"人格来源 / 人格切换语义 / 会话 meta"三行；路线图勾选 persona。
5. **不抽 interface**：唯一实现用具体 struct；第二来源出现时在**使用方**抽接口 + 编译期断言。
6. **CLI 参数防护**：位置参数 fail fast，flag 拼错立即暴露（不是静默降级）。
7. **budget 守门**：人格正文 ≤1500 字符（system 在截断中保留，加长挤占历史预算），测试守门。

## 8. 决策记录（本会话无重大分歧，以下为主要决策）

| 决策 | 结论 | 依据 |
|---|---|---|
| 深入方向选择 | 先做字段细化 + 装配统合；eval 等四项暂缓 | 代入感/一致性是当前短板；eval 等需要先积累使用反馈 |

## 10. 后续开发的统一与连贯性（新增对齐项）

1. **提示词装配唯一入口**：`persona.Compose`——后续任何 prompt 结构改动（注入位置、指令优先级、新字段）都收敛在 Compose 内，main 不散落拼接。
2. **人格字段只增不破 API**：`Get/List/Default` 签名冻结；新字段走 frontmatter + `Persona` struct 追加。
3. **文档先行**：本阶段先更新 `persona.md`（§4/§11/§13）再动代码，符合"每个里程碑先文档后代码"。
4. **评估先行理念**：将来的人格优化（注入位置、示例选择）必须配 eval 量化验证，不靠"感觉变了"——否则优化无法回归。

## 12. 推荐学习（同频清单，按优先级）

1. **LLM 评估方法论**（LLM-as-judge、黄金测试集、一致性度量）——**最优先**：没有评估，一切人格优化都无法验证好坏，只能凭感觉。

5. **记忆系统取舍**（注入 vs 检索 vs 向量）——已在 memory 模块讨论过，扩展理解"人格记忆 = 同一引擎 + 人格维度过滤"。
