## 1. 本会话解决的问题与边界

### 1.1 问题

对照市面 AI agent 的标准工具清单（read_file / read_subtree / write_file / str_replace / propose_* / glob / find_files / code_search / read_docs / run_terminal_command），盘点本项目缺哪些工具、各自用什么方法实现、有什么取舍；随后把"文件系统工具族"（读增强 + 写族 + 提议族）从方案到实现全量落地，全程保持项目既有原则：**零新增依赖、fail-closed、确定性优先、依赖单向**。

### 1.2 落地清单（全部 ✅ 2026-08-28）

| 工具 | 落点 | 核心行为 |
|---|---|---|
| file_write | builtin/file_write.go | 整体覆盖 + 原子写（temp+Rename）+ 保留原权限 + 不自动建目录 + Confirm fail-closed |

## 2. 用户补充细节的评估与落地情况

### 2.1 写侧（str_replace）细节

| 细节 | 结论 | 落地情况 |
|---|---|---|
| 多组 old/new + allowMultiple | ✅ 合理 | replacements 数组 + `allow_multiple` 开关（默认 false，唯一匹配） |
| 行尾归一化（\r\n→\n 匹配，事后恢复） | ✅ 合理 | 统一在 \n 空间替换，CRLF 文件落盘后保持原风格 |
| 失败累积 messages | ✅ 合理 | 单组失败不中止，全部失败才返回"文件无变更" |
| 缩进容错（暴力猜缩进级数） | ❌ 砍掉（定案） | 模糊匹配：命中唯一性与"按猜测缩进重写"语义都难保证；失败回灌 + file_read 看原文更确定 |
| 去空白兜底（剥空白匹配反推位置） | ❌ 砍掉（定案） | 对代码是危险的模糊替换（空白是语法/格式一部分），反推字节偏移复杂难验证 |

**决策依据**：确定性优先——"严格匹配失败 → 业务失败回灌 → 模型 file_read 看原文重试"的闭环成本极低（file_read 已在手），不值得用两级模糊匹配链换取"少重试一轮"。

### 2.2 读侧（read_files）细节

| 细节 | 结论 | 落地情况 |
|---|---|---|
| 窗口化 offset-limit（超界提示/续读建议） | ✅ 合理 | 完整落地：`[file_read: 共 N 行，offset=X 超出]` + `（继续可 offset=N+1…）` |
| 整读参数化（行数/字符/token 上限） | ⚠️ 结构合理，数值不照搬 | 保留"超限跳过 + 前缀截断"结构；数值对齐本项目（10MB 跳过，不做 50K/BPE） |
| `.env` 敏感文件 IGNORED | ✅ 合理 | fail-closed 拒绝读取；写侧靠 Confirm 兜底 |
| 常量忽略集（node_modules/*.min.js 等） | ✅ 合理 | 落地，与"跳隐藏目录"并存，只作用于遍历 |
| gitignore 遵循 | ⚠️ 合理但降级 | 够用版（嵌套/转义/`**` 跨层不支持），B 档转本次落地 |
| referencedBy（符号引用映射） | ❌ 不做 | 依赖符号索引 + 调用者映射，量级不匹配 |
| BPE token 估算 | ❌ 不做 | 与"字符粗估"哲学直接冲突 |
| 四级截断 + 符号分数 + 内存文件树 | ❌ 不做 | 全部依赖符号索引 |

### 2.3 实际对话反馈驱动的补缺

- **现象**：用户实测"把 README.md 的 JSONL 改成 JSON Lines"，模型臆造了 `doc_search({"query":"JSONL","path":"README.md"})`——**path 参数当时不存在**，宽容 JSON 解析静默忽略，实际搜了全工作区。
- **结论**：这不是模型笨，是工具缺"限定范围搜索"能力。**给 doc_search 补上真 path 参数**（文件/子目录限定，显式点名不受忽略集限制），模型就不用编参数了。

## 3. 踩坑记录

### 3.1 运行错误：internal/temp.go 编译失败（用户提问重点）

- **现象**：全量 `go test` / `go build` 报 `internal/temp.go:1:1: expected 'package', found temp`。
- **根因**：工作区出现一个内容仅为 `temp` 的无效 Go 文件（用户测试残留），放在 `internal/` 包目录下，整个包编译期直接失败；`internal` 是全部上层包的依赖，连锁挂掉 main/agent/builtin 等全部构建。
- **排查**：`go test ./...` 的输出中 `FAIL small/internal [setup failed]` + 具体到 `temp.go:1:1` 行号——setup failed 是编译期失败的典型标识，顺着报错行号定位到文件即可。
- **解决**：与用户确认后删除 `temp.go`，全量构建恢复。
- **教训**：`internal/` 包目录不允许出现任何非合法 Go 文件（哪怕叫 temp.go）；此文件已被 system-reminder 反复提示打开，属用户手动创建，删除前需确认。

### 3.2 gitignore 前导斜杠锚定失效

- **现象**：`/dist/` 规则（锚定 root 的目录忽略）不生效。
- **根因**：解析保留前导 `/`，`filepath.Match("/dist", rel)` 对相对路径永不命中。
- **解决**：解析时 `TrimPrefix(t, "/")`——本项目匹配本就相对工作区根，前导斜杠语义等价，可安全去掉。

### 3.3 gitignore 规则顺序取反失效

- **现象**：`*.log` + `!keep.log` 时 keep.log 仍被忽略。
- **根因**：最初从后往前遍历（想实现"最后匹配生效"），导致靠前的 `*.log` 最后处理覆盖了取反。
- **解决**：改从前往后遍历，靠后规则自然覆盖靠前——`!keep.log` 在 `*.log` 之后，取反正确生效。

### 3.4 其余小坑（测试层）

- file_write 测试用例用了不存在的父目录，恰好撞上"不自动建目录"约束（验证了约束真实生效）；字节数断言从直觉的 12 修正为实际 6。
- file_tree 极小 budget 时输出空——补"预算耗尽"提示分支（区分"省略 N 个文件"与"一个都没装下"）。

## 4. 权限与工具职责分离：效果与解决的问题

### 4.1 分离前的问题（为什么需要横切）

权限横切层落地前，项目里**确认机制四处分散、各自为政**：

| 位置 | 机制 | 问题 |
|---|---|---|
| 命令层 | `Spec.Perm` + `Registry.Confirm`（走 policy） | ✅ 唯一正确的形态 |
| exec | `ExecConfig.Confirm` 回调 | 工具内部各自实现 |
| file_write / file_edit | `FileConfig.Confirm` 回调 | 同上 |
| propose 落地 | main 里手写 if 块 | 特例逻辑 |

四个痛点：新增 Ask 工具要再抄一份确认回调（重复实现）；组合根要分别记得注入各处 Confirm（漏了即裸奔）；无法集中审计"哪些工具需要确认、确认是否到位"；改确认行为（如弹窗文案）要改多处。

### 4.2 分离后的职责与组合

| 层 | 职责 | 落点 |
|---|---|---|
| 声明层 | 工具只做功能；权限静态声明（**不进 Spec**，防污染模型视角） | `builtin.ToolPermissions` |
| 判定层 | 执行前统一拦截：Pass 放行 / Ask 走确认 / 无回调拒绝 | agent `guard` |
| 交互层 | 确认弹窗、读用户输入（**命令与工具共用**） | main `confirmName` |

组合链：`builtin.ToolPermissions（声明）→ agent.guard（判定）→ main.confirmName（交互）`——三层各司其职，职责单向。

### 4.3 效果

1. **新增 Ask 工具 = 登记权限表一行**，确认交互零代码（工具内部不再写确认逻辑）。
2. **单一事实来源**：哪些工具 Ask 一眼可见（权限表全量列举）。
3. **fail-closed 由 agent 硬约束**：Ask 无确认回调即拒绝，不再依赖组合根"记得注入"——安全保护下沉到机制而非人。
4. **命令与工具共用同一 policy 类型 + 同一 confirmName**——横切不分裂，无第二套确认系统。
5. **拒绝语义统一**：业务失败回灌，模型收到拒绝自行调整（与 exec 现状一致）。
6. **防漏机制**：注册校验"注册名 ∈ 权限表"，新增工具漏登记在注册期暴露（fail-fast）。

### 4.4 解决了之前的哪一项遗留

本文件 §6 遗留表首行"完整权限横切层（propose 只是最小形态）"→ **已解决（2026-08-28 权限横切层落地）**；propose 从"最小形态"升级为通用机制的一个实例（其落地确认保持独立，属落地语义）。

## 5. 开发风格延续

权限横切层落地是"职责分离 + 横切关注点单列"的样板，后续开发按以下方式延续：

1. **横切能力三件套**：新增横切关注点（trace / policy / 观测）一律按"**声明层 + 拦截/事件层 + 装配层**"展开——功能进工具、策略进声明、交互进组合根，agent 循环只暴露最小钩子（Option + nil-safe 回调）。
2. **标准流程五步**（已写入 CLAUDE.md"新增内置工具的标准流程"）：一工具一构造函数 → 注册 → **权限登记（写/执行=Ask，只读=Pass，防漏由注册校验兜底）** → 提示词 → 验证。新增工具照此执行，缺一步即不完整。
3. **Ask 工具零确认代码**：确认交互由 agent 权限层统一提供，工具作者只登记权限表——"声明式权限"取代"命令式确认"。
4. **fail-closed 不因装配遗漏而松动**：安全相关约束尽量**下沉到机制**（agent 层硬约束）而非依赖人记得注入（组合根）。
5. 延续既有约定：文档先行（Zoo/model 定稿再动码）、决策同步 CLAUDE.md 决策表、imports_test 固化依赖单向、合并门槛（race / vet / gofmt）全绿。
