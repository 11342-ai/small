# 踩坑记录（Gotchas）
> 每次踩过的坑与预防办法。原则：记录根因，不记录表象；给出预防，不重复踩。

## 1. 流式空闲超时挂死（streamCtx 未贯穿建连）
- 现象：`TestStream_IdleTimeout` 挂死，`panic: test timed out after 30s`，`Scanner.Scan()` 永久阻塞。
- 根因：HTTP 请求绑定的是外层 `ctx`，而 `streamCtx` 是拿到 2xx 后才创建的。`http.Transport` 只监听 `req.Context()`——空闲超时取消 `streamCtx` 时，transport 的读毫无感知。
- 预防：
  - 要中断 HTTP 读，取消必须作用在 `req.Context()` 上（请求绑定会被取消的 ctx）。
  - streamCtx 在发请求前创建、请求绑定它；空闲计时器仍只在 2xx 后启动。
  - 超时/取消类测试用挂起的 handler（`<-r.Context().Done()`）锁时序，否则 server 先 EOF 会让断言飘。

## 2. GoLand 读不到 shell export 的环境变量

- 现象：终端里 `export DEEPSEEK_API_KEY=...` 后，GoLand 运行仍报 `environment variable ... is required`。
- 根因：`export` 只对那个 shell 及子进程生效；GoLand 用 IDE 进程自己的环境，与任意终端无关。
- 预防：在 Run Configuration 的 Environment variables 里配；或终端 `go run .`；或代码支持 `.env`（未启用）。

## 3. `http.Client` 没有 `Clone` 方法

- 现象：`c.httpClient.Clone()` 编译报错 `no field or method Clone`。
- 根因：记错了 API——`http.Client` 不存在 `Clone`。
- 预防：手动拷贝需要保留的字段（`Transport`/`CheckRedirect`/`Jar`），`Timeout` 置 0。

## 4. adapter 参数形态反复（接口 ↔ 具体类型）

- 现象：`NewProviderChat` 参数在 `*provider.Client` 与 `provider.Completer` 间往返。
- 根因：两个诉求打架——具体类型直白、能力完整；接口可 mock、但窄化能力（拿不到 `Stream`）。后来加流式降级探测，字段必须是接口（多态载体），才定下来。
- 预防：功能需求决定形态——要探测多态，就必须接口；不要为"用接口"而用接口。

## 5. 529 是 Cloudflare 私有扩展码

- 现象：列重试状态码时写"408/429/5xx/529"，529 与 5xx 重复，语义矛盾。
- 根因：529（Overloaded）不是 IANA 注册码，是 Cloudflare 私有扩展，属 5xx 区间，肌肉记忆单独拎出来了。
- 预防：重试状态码 = 408/429/全部 5xx，529 自然落在 5xx 内，无需单列；用 `ShouldRetry` 谓词可配置。

## 6. 测试必须覆盖边界路径

- 现象：早期测试只写 happy path，超时/取消/非法 chunk 都没覆盖。
- 根因：边界 bug（见 #1）正是靠边界测试逼出来的——只测正常路径等于没测。
- 预防：流式至少覆盖——空闲超时、外部取消、回调中止、非法 chunk、EOF 无 `[DONE]`、流中失败不回退（请求数 = 1 断言）。

## 7. 空 turns / 空 choices 是真实边界

- 现象：adapter 早期把空消息体直接发出去（远端 400），空 choices 会静默出错。
- 预防：`Complete` 入口空 turns 提前报错；响应空 choices 报错；`role/content` 白名单不做（合法角色由领域层保证，别把领域规则塞进适配层）。

## 8. 依赖方向 ≠ 直觉的"谁被塞进谁"（session 案例）

- 现象：`session` 被塞入 `agent.New`，直觉上以为依赖该是 `session → agent`，实际是 `agent → session`，与直觉相反。
- 根因：依赖方向 = import 方向 = "谁需要谁"。构造注入（把 X 塞进 Y）要求 Y 的代码 import X 才能引用其类型并调用，所以注入必然产生 `Y → X`。把"数据流方向"（agent 的 Turn 流进 session）或"服务关系"（agent 消费 session）误当成了依赖方向。
- 预防：
  - 判断依赖方向只看 import，不看"谁装谁"、不看数据往哪流。
  - "把 X 塞进 Y" ⇔ "Y 依赖 X"，任何语言一致。
  - 推论（循环陷阱）：session 一旦被塞进 agent（`agent → session`），session 就不能再 import agent，否则循环——故存储部件必须自持数据模型（session.Message），`Turn↔Message` 翻译放 agent 侧（persist.go）。若想让 session 直接存 agent 的领域类型（`session → agent`），则 session 必然是 agent 的上层外壳而非部件，注入方向整体反转。

## 9. 依赖纪律的"真风险"与"伪风险"（编译器兜底认知）

- 现象：盘点四个依赖纪律风险点（隔离点破坏 / 父子包反向 / 存储越界 / 重试越界），直觉上都像隐患；逐一验证后，只有一个是真的。
- 根因：Go 的循环 import 是编译期硬拦截——凡是构成环的依赖（`tool↔builtin`、`agent↔session`、`provider↔retry`）一旦被写出来，build 立即红，无潜伏期，属于"伪风险"（编译器既得保证，不是取舍也不是偷懒）。唯独"agent 包内非 adapter.go 文件 import provider"不构成环（provider 不 import agent），编译器放行——这才是唯一需要人守的"真风险"。
- 预防：
  - 真风险用测试固化：`internal/agent/imports_test.go` 用 `go/parser` 断言"import provider 只出现在 adapter.go"——把软纪律变成合并门槛（红线 6）的一部分，靠人肉记得不如靠门槛拦。
  - 伪风险不动代码：三个伪风险不在代码层面设防（编译器已兜底），认知记在此处即可，避免未来误以为要"修复"。
  - 远期扩展点：若第二个模块也要消费 `agent.Turn`，再评估上提 `internal/domain`（届时 `session.Message` 镜像可消除），记录在 `session.md` 待决问题。

| 风险 | 位置 | 约束 |
| :--- | :--- | :--- |
| 隔离点被破坏 | agent 包内非 adapter.go 文件 import provider | 生产代码已实测只有 adapter.go 一处，未来新增要守 |
| 父子包反向 | tool 反 import tool/builtin | tool/builtin → tool 单向；反向即成环 |
|存储部件越界 | session import agent | 踩坑 #8 已记：会成 agent → session → agent |
|重试子包越界 | provider/retry import provider | provider → retry 单向；反向即成环 |

## 10. 工具回灌形态混用（JSON 与文本混在一段）

- 现象：`k8s_evidence` 的"回灌是合法 JSON"断言失败：`invalid character 'è' looking for beginning of value`（`'è'` 是"证"的 UTF-8 首字节被解析器报出来的样子，报错本身很费解）。
- 根因：Data 写成 `"证据包已落盘: <path>\n\n" + JSON`——整段不再是单个 JSON 文档；下游（测试辅助、评测脚本）只能按固定文案 `TrimPrefix` 剥前缀，文案一改（换英文、多个空格、路径格式变化）就静默失效。
- 预防：
  - 一个工具的 Data 只能二选一：机器解析的 JSON，或人读的文本，同一工具不混。
  - 定形后测试辅助跟着分：`execToolOK`（断言纯 JSON）与 `execToolText`（只断言非空）。回灌形态不同的工具共用同一断言，就是这个 bug 的温床。
  - 落盘路径这类"元信息"不要靠拼字符串塞进 Data：要么由命名约定确定（`<ns>-<pod>.evidence.json`），要么进结构化字段。

错误示例（拼串混形态）：

```go
return tool.Result{Data: "证据包已落盘: " + path + "\n\n" + data}, nil // ✗ 整段不再是 JSON 文档
```

消费侧只能按固定文案剥前缀（`strings.TrimPrefix(res.Data, "证据包已落盘: "+path+"\n\n")`）——文案或路径格式一变就静默失效，`TrimPrefix` 没剥到也不报错。

正确示例（形态二选一）：

```go
// 机器解析的：只回 JSON；落点靠命名约定（<ns>-<pod>.evidence.json）
return tool.Result{Data: data}, nil

// 人读的：路径 + 渲染后的文本；断言相应换成 execToolText（只要求成功且非空）
return tool.Result{Data: "报告已落盘: " + jsonPath + "\n\n" + md}, nil
```

想两者兼得：把元信息做成结构化字段（`{"saved_to": "...", "evidence": {...}}`，Data 仍是纯 JSON），而不是拼字符串——代价是模型读证据时多一层。

## 11. 对外参数结构直接复用内部类型 / 缺 json tag（三类静默失配）

- 现象：模型按 schema 发出的键收不到，且都不报错——`pod` 匹配不上字段 `Name`；`since_seconds` 匹配不上 `Since`；`Since` 声明为 `time.Duration` 时，3600（秒）被当成 3600 纳秒；嵌套的内部类型 `k8s.LogQuery` 无 tag 时 `tail_lines`/`limit_bytes` 同样失配。症状是"必填校验永远报缺参数"或"时间窗/字节上限永远走缺省"。
- 根因：Go 的 json 解码只做字段名的大小写不敏感匹配（`namespace` ↔ `Namespace` 能中，`pod` ↔ `Name` 不能），没有 tag 就没有契约；带单位的量未换算就直接落进 `time.Duration`/`int64`。
- 预防：
  - 对外参数字段一律带 json tag；单位量用基本类型 + 显式换算（`time.Duration(in.SinceSeconds) * time.Second`）。
  - 内部类型（采集包的 `LogQuery` 之类）不直接当参数结构用：工具侧定义平铺参数，再组装成内部类型。
  - 编译期查不出这类错，写完用"按 schema 造一份载荷解码并断言每个字段"的最小脚本核一遍键名（可只放 /tmp，不进仓库）。

## 12. 嵌入字段加 tag 会改变 JSON 形态（静默变空）

- 现象：`type reportArgs struct { Namespace, Pod string; k8s.ReportView }` 若把内嵌写成 `k8s.ReportView \`json:"report"\``，模型发的平铺键全部收不到，字段静默为空（多余键被忽略，不报错）。
- 根因：内嵌字段不带 tag 时，JSON 编解码把它"内联"（等同把字段摊平写在外层）；一旦带 tag 就变成嵌套对象，必须 `{"report":{...}}`。
- 预防：用嵌入来"摊平字段"时绝不加 tag；要嵌套就显式写嵌套结构。改嵌入字段的 tag 属于契约变更，要同步改 schema 与载荷核对脚本。

## 13. 工具 Description 承诺的字段必须真的返回（误导性证据比缺字段更糟）

- 现象：`k8s_workload` 的 Description 写了"模板 resources/probes、replicas、strategy、conditions"，实现却调了 `coll.Pod`（返回 Pod 视图）——两个工具返回同一份数据，承诺的字段永远不出现。模型据此会判断成"集群里没有这些字段"。
- 根因：六个薄壳靠复制骨架写，改动只落在函数体里，没人回头核对"Spec 承诺 vs 实际返回"。
- 预防：Spec 的 Description 与"转发到哪个采集方法"必须一一对照复核；把关键行为写成真集群断言（如 `strings.Contains(w, "\"kind\": \"Deployment\"")` 锁"上溯到 Deployment"）。

## 14. 派生 ctx 覆盖入参 + 提前 cancel（fake 测不出，真集群才暴露）

- 现象：`WorkloadOf` 里 `ctx, cancel := c.callCtx(ctx)` 覆盖了入参，Get 完立刻 `cancel()`，随后用同一个 `ctx` 去查 ReplicaSet，报 `client rate limiter Wait returned an error: context canceled`。单测全绿，真集群冒烟才发现。
- 根因：变量重用——`ctx` 已被替换成"会随 cancel 失效的子 ctx"，后续调用拿到的是已取消的上下文。
- 预防：
  - 派生 ctx 一律另起名字（`pctx, cancel := ...`）；`cancel` 只覆盖它创造的那次调用，跨调用要传父 ctx。
  - 真实的传输语义（ctx、限流、超时、字段实际取值）必须有一次真集群冒烟：fake 客户端不走 HTTP/限流，这类问题它看不见。

## 15. fake clientset"构造成功"不等于"能查到"

- 现象：`metricsfake.NewSimpleClientset(podMetrics)` 之后 Get 报 `pods.metrics.k8s.io "x" not found`。
- 根因：生成的 fake 用资源名 `pods` 取数，而 ObjectTracker 从 Kind `PodMetrics` 猜出的资源名是 `podmetrics`——对象注册进了另一个"桶"。
- 预防：凡"生成型 fake 包"（metrics、custom-metrics 这类小型 API 组），先写一条最小 Get 断言确认取得到；或直接用 reactor 显式应答（`PrependReactor("get", "pods", ...)`）绕开命名不一致。

## 16. 断言写死会"闪动"的状态值

- 现象：断言 `waiting.reason == ImagePullBackOff` 偶发失败——kubelet 退避重试期间会短暂回到 `ErrImagePull`。
- 根因：把 k8s 的瞬时状态当成稳定值；退避是周期性的，状态本身在跳。
- 预防：断言"属于失败集合"而不是单一取值（`ImagePullBackOff` 或 `ErrImagePull`）；等待用轮询（等 reason 到达期望值），别用固定 sleep。

## 17. 零值 Collector 的可用边界（别顺手拿它跑成功路径）

- 现象：用 `&k8s.Collector{}` 做"注册断言/参数校验"没问题；拿它跑成功路径会得到"产物目录未配置"的业务失败，若代码里再用 nil 客户端就 panic。
- 根因：零值既没有 `cfg`（`Dir` 为空）也没有客户端；而构造函数在装配期只声明 Spec 与闭包、不碰这些，所以零值只在这两类路径上安全。
- 预防：零值只用于不触达 IO/网络的断言（装配、参数校验）；要跑成功路径就注入 fake 客户端或连真集群。

## 18. 降级分类要按"这个来源本该存在吗"分两面（裸 Pod 不是必需来源失败）

- 现象：真集群首轮跑场景集，通用断言红——裸 Pod（无 controller owner）的"工作负载取不到"被记成 `required_failed`，于是每条裸 Pod 场景都凭空多一条"缺失证据"，还压置信度。
- 根因：把"某个来源读失败"直接等同于"证据缺失"。裸 Pod 本来就没有上层工作负载这一层，那是 `no_data`（来源正常、确实没有），不是失败。
- 预防：
  - 降级分类的判据取自数据而非错误文本：先看 `ownerReferences` 里有没有 controller owner，有才要求取到（`required_failed`），没有就是 `no_data`。
  - 同一思路已在日志侧：400/无可读日志记 `no_data`，权限/超时/连接失败才记 `required_failed`——否则 ImagePullBackOff 这类"压根没有日志"的场景会凭空多出缺失证据。

## 19. 等待与断言别绑瞬时态与第三方文案（同 #16，另两类）

- 现象一：场景 up 时等 `container_state_reason=CrashLoopBackOff`，180s 等不到。
- 现象二：ImagePull 场景断言绑死报错里的 `not found`，registry 一抖动就变成 `EOF` 而误红。
- 根因：崩溃容器退避到后面，kubelet 把状态长期留在 `terminated`/`Error`，只有退避周期里短暂回到 CrashLoopBackOff；拉取失败的文案由 registry + CRI 决定，不由我们决定。
- 预防：
  - 崩溃类场景用"上次终止原因 + restartCount ≥ 1"这类稳定判据；等待一律轮询，别用固定 sleep（延续 #16）。
  - 只断言稳定片段（如 `failed to pull image`、请求的镜像引用），把"404/403/EOF 的差别"交给场景 README 声明前置条件 + 人复核。

## 20. "日志取不到"要分清"确实没有"与"读不到"

- 现象：断言 previous 日志里有崩溃输出，稳定失败。
- 根因：minikube + containerd 下 previous 常取不到，且它不是错误——正文是 `unable to retrieve container logs`（200 带着这句提示），而真正的 fatal 就在当前日志里。
- 预防：断言"两次日志合起来能看到"而不是"previous 里有"；采集侧按 #18 的规则给日志失败分类（400/空 → `no_data`），别让"没有上次运行"变成缺失证据。

## 21. 不可容忍 taint 的两个 k8s 事实（默认容忍、事件不列键）

- 现象：断言"Pod 的 tolerations 为空"直接红；用 taint 键（`diag-lab-scenario`）当判分关键词，在事件里找不到。
- 根因：API server 会给每个 Pod 注入 `node.kubernetes.io/not-ready` 与 `unreachable` 两条 NoExecute 默认容忍；本版调度器文案是 `1 node(s) had untolerated taint(s)`，不列出是哪把 taint。
- 预防：断言写成"没有容忍本场景那把 taint"（按 key 前缀判）；"是哪把 taint"只能从节点侧证据（`k8s_nodes` 的 `taints`）看，判分关键词与判别线索也要落在节点侧。

## 22. 节点级前置要脚本化（场景钩子），别靠人肉 kubectl

- 现象：taint 是节点对象，写不进场景的 `manifest.yaml`（那只能 apply 命名空间内的对象）。
- 根因：一旦靠手敲 `kubectl taint` 准备前置，就一定会忘摘——单节点集群上 NoSchedule 会封掉唯一可调度目标，后续场景全部 Pending，而报错看起来像"另一个场景坏了"。
- 预防：场景目录支持可选 `setup.sh`/`teardown.sh`（up 前跑 setup、清理后跑 teardown、`down-all` 对每个带 teardown 的场景都跑一遍）；钩子必须幂等（重复触发无害），teardown 还要复查一遍并在没清干净时打警告。

## 23. 造测试前置之前，先实测最小假设（伪 registry 被两条硬事实否掉）

- 现象：为了造"私有仓库缺凭据"，想用 busybox httpd 冒充 registry 返回 401；实测两处都过不去。
- 根因：把"HTTP 服务"当成"registry 协议"（containerd 对 plain HTTP 的 registry 按 HTTPS 处理，要改节点 containerd 配置并重启），且没先核对目标二进制的选项集（busybox 1.36 的 httpd 没有 `-a` 认证参数，认证走配置文件另一套语法）。
- 预防：
  - 先用最小命令验证关键假设（一条 `crictl pull` + 目标二进制的 `--help`），再谈方案；否决方案时把"哪条命令的哪句报错"记下来。
  - 挑现成服务时要看报错是否可区分：Docker Hub 把两种原因写在同一句（`repository does not exist or may require authorization`），与"镜像名错"撞车；ghcr 上匿名拉私有路径给的是干净的 403，能唯一归因（代价是依赖外网可达，要在 README 里声明）。

## 24. 要确定性就给节点预置镜像，别赌 registry

- 现象：OOM 堆错配场景需要真 JVM 镜像，而本机到 Docker Hub 会抖。
- 根因：把"评测可复现"押在网络与公共仓库的可用性上。
- 预防：主机已有的镜像用 `minikube image load` 塞进节点（tag 非 latest → 默认 `IfNotPresent` 直接用本地），之后场景完全离线；一次性准备命令写进场景 README 与脚本注释。

## 25. RBAC 最小集要从调用反推，并且拿受限凭据实测一遍

- 现象：文档里那张"RBAC 最小集"漏了 `nodes` 的 `list`；照它授权会让 `k8s_nodes`（Pending 归因的唯一入口）直接 403。
- 根因：清单是按"要读节点信息"的印象写的 `nodes get`，而代码里 `Nodes()` 走的是 `Nodes().List`——凭印象写权限，漏 verb 是必然。
- 预防：
  - 清单从代码里每个 client 调用反推（精确到 verb 与作用域；注意 `Pods("")` 这种集群范围 list 不是命名空间级 Role 能满足的）。
  - 再拿只读 SA 把每个端点打一遍（`auth can-i` 覆盖无对象可试的项，metrics 走 `--raw` 实测），并做反向检查：未授权的动作（如 `secrets` get、`pods` delete）必须 Forbidden，证明没多给。

## 26. 判分与评测口径要用历史产物校准，别凭直觉立规则

- 现象：按"申报了 `missing_evidence` 就是把没查清"的直觉，给缺失声明加了"多报扣分"，结果 14 份满分报告里 13 份被扣。
- 根因：证据包的 notes 只覆盖采集器自己的来源读失败，而报告里的 `missing_evidence` 是模型视角的证据缺口，天然更大；把两者当成同一个集合了。模型还明确写着"不影响结论"，扣分等于把如实申报当错误。
- 预防：
  - 改判分规则前，先拿已归档产物跑一遍看命中面；命中面过大（像这次 13/14）基本说明规则在测错东西。
  - 只判客观判得了的方向（漏报），把判不了的部分（多报的对错）降级成提示交人复核，别硬判。

## 27. 关键词比对要先归一化（`last_state` vs `lastState` 不是模型的错）

- 现象：expect 里写 `lastState`，模型写 `last_state`，判分算未命中。
- 根因：判分做的是精确子串比对，而命名风格是自由的（Go 驼峰 / JSON 下划线），两边各写一种就漏判。
- 预防：比对前统一归一化（小写 + 去下划线/连字符/空格），并给归一化本身写一条单测，免得以后被"优化"掉。

## 28. 片段替换的锚点要带足上下文（吞掉相邻行的教训）

- 现象：改代码用片段替换时，old_string 少写了紧随其后的一行，于是那行（`stream, err := ...GetLogs(...).Stream(ctx)`）被一起删掉，编译红才发现；另一次把两行注释粘成了一行。
- 根因：把"要紧跟在后面的、需要保留的行"排除在替换范围之外，替换后边界不清。
- 预防：替换锚点带足上下文（要么把要保留的相邻行也写进 new_string，要么扩大 old_string 的范围让边界唯一）；改完立刻 `gofmt`/`go vet`/`go test`，别攒着一起跑。
