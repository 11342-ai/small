ebpf helper
- Map操作函数实现数据共享
- 网络处理函数用于XDP/TC程序
- 追踪观测函数采集系统信息
- 事件通知函数发送数据到用户态

###### 常见的 Helper 函数
内存读写
bpf_probe_read(dst, size, src) — 安全读取内核/用户内存，自动处理越界。变体 bpf_probe_read_kernel
bpf_probe_read_user(dst, size, src) — 只读用户空间内存
bpf_probe_write_user(addr, data, size) — 写用户态内存（需 CAP_SYS_ADMIN）

Map 操作
bpf_map_lookup_elem(map, key, value) — 查找
bpf_map_update_elem(map, key, value, flags) — 更新，flags=BPF_ANY/BPF_NOEXIST/BPF_EXIST
bpf_map_delete_elem(map, key) — 删除
bpf_map_get_next_key(map, key, next_key) — 遍历 key

上下文信息获取
bpf_get_current_pid_tgid() — 返回 pid<<32|tgid，低32位是线程ID，高32位是进程ID
bpf_get_current_uid_gid() — 同理，uid/gid
bpf_get_current_comm(buf, buf_size) — 进程名
bpf_get_current_uid_gid_proto() — 用于 socket 场景
bpf_ktime_get_ns() — 纳秒级时间戳
bpf_ktime_get_boot_ns() — 从 boot 开始算的时间
bpf_ringbuf_output() / bpf_ringbuf_reserve() — 高性能 ring buffer 输出
bpf_perf_event_output(ctx, map, flags, data, size) — perf buffer 输出

网络相关
bpf_skb_load_bytes(skb, offset, buf, len) — 从 skb 读取数据
bpf_skb_store_bytes(skb, offset, buf, len, flags) — 写入 skb
bpf_csum_update(skb, csum) / bpf_l4_csum_replace() — 校验和计算
bpf_skb_change_tail(skb, len, flags) — 修改 skb 长度
bpf_redirect(ifindex, flags) — XDP/TC 重定向
bpf_xdp_adjust_head(xdp, offset) — 调整 XDP 数据指针
bpf_fib_lookup(ctx, params, size, flags) — FIB 查找

程序调用链
bpf_tail_call(ctx, map, index) — 尾调用另一个 bpf 程序
bpf_ktime_get_ns() — 获取时间

栈追踪
bpf_get_stackid(ctx, map, flags) — 获取栈回溯 ID
bpf_get_current_stackid() — 获取当前栈

混淆点：
bpf_probe_read vs bpf_copy_from_user：前者更安全，自动检查；后者是强制拷贝
bpf_ktime_get_ns vs bpf_clock_gettime：前者是内核时间，后者通过系统调用
bpf_ringbuf_output vs bpf_perf_event_output：ringbuf 更高效，零拷贝；perf 需要额外拷贝到 perf buffer
bpf_redirect vs bpf_clone_redirect：前者直接转发 skb，后者克隆一份再转

###### 常见数据结构
task_struct — 内核任务描述符

签名：struct task_struct *
场景：进程/线程追踪、调度分析、权限检查
代表：系统中每一个进程或线程
混淆：struct task_struct vs struct pid：前者是内核内部结构，后者是 PID 命名空间的抽象。访问当前任务用 bpf_get_current_task() 返回的是 struct task_struct*
pt_regs — 寄存器快照

签名：struct pt_regs *（kprobe 入口）或各架构变体
场景：系统调用参数读取、函数参数追踪
代表：CPU 寄存器状态，用于恢复调用现场
sk_buff — 网络数据包

签名：struct sk_buff *（tc/xdp）或 struct __sk_buff（bpf 简化版）
场景：网络包处理、流量监控、防火墙
区别：struct sk_buff 是完整内核结构，__sk_buff 是 bpf 辅助结构，只暴露部分字段
sock — socket 描述符

签名：struct sock *
场景：连接追踪、socket 分析
bpf_perf_event_data — perf 事件数据

签名：struct bpf_perf_event_data *
场景：性能分析、采样
包含：regs、sample_type 等

###### 最小闭环监测
最小闭环 = 触发点 → 采集 → 过滤/聚合 → 输出 → 用户态消费

选择触发点：
- tracepoint（最稳定）：tracepoint/syscalls/sys_enter_openat
- kprobe/uretprobe：内核函数入口/返回
- raw_tracepoint：更低开销
- XDP/TC：网络包处理

最小示例思路：
1. 用 tracepoint/sched/sched_switch 捕获调度切换
2. 用 bpf_map 存当前进程状态
3. 用 bpf_ringbuf 输出关键事件
4. 用户态用 bpftrace 或自写程序消费
避免过度监控：先确定你要解决什么问题，再选最细粒度的触发点。

###### 数据来源与时序

数据来源：
- tracepoint：稳定路径，字段在 /sys/kernel/debug/tracing/events/<category>/<name>/format
- kprobe：自己定义要读哪些参数
- perf events：看 perf_event_attr 配置
- 查看 bpftool prog dump <id> 找 attach 目标

时序保证：
- eBPF 程序在禁抢占上下文执行，天然串行
- 跨 CPU 需要用 per-CPU map 或加锁
- 时间戳用 bpf_ktime_get_ns()，可计算延迟
- 用 bpf_seq_printf 或 ringbuf 里的 timestamp 字段来排序

顺序问题：
- 单核内严格按时间顺序
- 多核输出需要用户态按 timestamp 重排序
- ringbuf 保证单核顺序，perf buffer 不保证跨事件顺序

###### 挂载点快速验证方法
第一个方法:分开查看
录制 : trace-cmd record -e sched_switch
查看 : trace-cmd report

第二个方法:刷屏

```
<...>-61466 [003] 52461.710561: sched_process_fork:   comm=runc:[0:PARENT] pid=61466 child_comm=runc:[0:PARENT] child_pid=61468
```

- 例如: 以挂载点 "tp/sched/sched_process_exit" 为例，， struct trace_event_raw_sched_process_fork = trace_event_raw_ + sched_process_fork
- 而且断言可以进行兜底 

断言兜底

```
那行，三条应该同时成立： child_pid == $! 、 parent_pid == $$ 、 /proc/$!/stat 的 ppid == $$ 。
这里 bash 是单线程 leader，tid 和 tgid 相等，所以不会踩口径的坑——适合当"第一层验收"
```

###### C语言的 extern 和那个 __ksym
extern 是C语言中的只声明，不定义:告诉编译器有这样子的一个符号，定义在其他地方。在 ebpf 里面，它的特殊含义就是 kfunc，是内核导出的函数，加载时由内核解析。那个 __ksym就是“这个是内核符号”的标记

它不在 vmlinux.h 里，因为 vmlinux.h 只有类型，没有函数。
- 类型（struct/enum）在 vmlinux.h
- helper 在 bpf_helpers.h/bpf_helper_defs.h，是带编号的静态内联桩
- kfunc 谁都不给声明，只能自己 extern + __ksym 写

###### 几个函数的区分
- bpf_get_current_task 是 helper，拿的是"当前正在执行的 task"，也就是触发这个 tracepoint 的那个任务，返回裸指针，没有引用计数，只能当场用
- bpf_task_from_pid(pid) 是 kfunc，按 pid 去查任意一个 task，返回的 task 带引用计数，跨 CPU 安全，所以能安全访问并可以留到后面用
- bpf_task_release 就是释放那份引用，把引用计数减回去。 bpf_task_from_pid 成功一次就多一份引用，不 release 就永远收不回 task_struct，等价于内核内存泄漏。

- fork 的上下文是父进程，新任务是 child，父进程手里没有孩子的指针，只能拿 ctx->child_pid 去查，所以必须用 bpf_task_from_pid ， bpf_get_current_task 帮不上

###### task_struct 中的 is_thread
两个取值，本质是布尔，C 里用 __u8 装。
- is_thread = 1 ：新任务的 tgid 不等于它自己的 pid，说明它和父进程同属一个线程组，是父进程创建的线程。
- is_thread = 0 ：tgid 等于它自己的 pid，说明它自立门户、成了新线程组的组长，也就是新进程。

exit 侧对应的字段是 group_dead ，同样是两个取值：1 是整组退出（进程真的消失了），0 是普通线程退出。两侧一个管生一个管死，口径要配着看

###### 排错的过程
**问题表述**
运行了专门用来进行紧循环系统调用的程序，使用 sudo trace-cmd stream -e sys_enter -P <pid/> 进行抓取，发现没有数据输出

**怀疑问题**
- 可能是那个给命令的pid出错，内核态和用户态的表不一致，但是后面排除这个选项，因为
    - 程序是单线程，pid、tgid、tid 三者相等
    - 一旦多线程，传主线程的号，只有主线程的事件会命中，工作线程因 tid 不同而漏掉
    - 如果跑在容器或 pid namespace 里，容器内看到的号是重映射的，和宿主上的不一致，那种情况要按宿主层的号过滤
- 时间窗口错位
    - trace-cmd 只记录它运行期间的事件
    - trace 那一段没覆盖 env1 真正在循环的时间，就是空的
- pid 不是同一个
    - 同一个号会被复用。你用一个已退出的旧实例的 99707 去过滤，当前活着的 env1 未必是这个号
    - 先起 trace 再起程序，你也无法提前知道它会拿到哪个号

**第二步骤**
./env1 & sudo trace-cmd stream -e sys_enter -P $!
sudo trace-cmd stream -e sys_enter -f 'common_pid == 101058'
也是没有结果

sudo sh -c 'echo 101058 > /sys/kernel/tracing/set_event_pid'
sudo sh -c 'echo 1 > /sys/kernel/tracing/events/raw_syscalls/sys_enter/enable'
sudo cat /sys/kernel/tracing/trace_pipe

sudo sh -c 'echo 0 > /sys/kernel/tracing/events/raw_syscalls/sys_enter/enable'
sudo sh -c 'echo > /sys/kernel/tracing/set_event_pid'
有了结果

**分析**
证明两件事：
- 事件名解析对了，pid 过滤键也对了，内核的过滤链路是通的。
- 同一个键换成 trace-cmd 却一条没有，说明差别只在 trace-cmd 内部，它没有把事件真正启到你读到数据的那个位置，或者它把这个过滤设到了别的地方。

最可能是这两种之一：
- 一是 trace-cmd stream 会新建自己的 tracing 实例，pid 过滤和事件启用没落在同一个实例上，结果读取的那个实例根本没启用事件
- 二是它把 pid 当成了 function tracer 的过滤口径，而事件侧什么都没留下。前者的表现正是你看到的空。

###### 类型对应问题
C语言中，long int = __s64

- C 侧 long int 在 x86_64 是 8 字节，正好和 u64 对上
- 但换到 32 位平台 long 是 4 字节，整个结构就错位了
- 所以议写成 __s64 或 long long，把宽度钉死

###### Go的unsafe库
- 它的作用就是绕过类型系统和内存安全约束，给必须突破类型系统的底层代码用的
**提供的东西**
- 一个 unsafe.Pointer 类型（可指向任意类型，能与 *T 互转，也能与 uintptr 互转）
- Sizeof、Alignof、Offsetof 三个编译期求值的函数，后来还有 Add、Slice

**功能与职责，典型用途**
- 一是按内存布局解释字节。ringbuf 给你的是一段没有类型的字节，用 unsafe 把首地址转成 *SysExit，就能零拷贝地读字段。这正是你项目里的用法。
- 二是编译期布局断言。unsafe.Sizeof 用在 var _ [目标 - Sizeof]byte 这种技巧上，逼编译器检查结构体尺寸，你 forkEvent 那两行就是了。
- 三是与外部世界对接。cgo、syscall、mmap、iovec，都需要把 Go 的内存地址交出去。
- 四是性能敏感处的零拷贝，比如 string 与 []byte 之间不复制内容。

**常见的滥用途径**
- 拿它当类型转换的捷径，把 []byte 当 string、把 int 当 float 硬转。这破坏类型安全，且转换结果不保证跨版本一致。
- 依赖结构体内存布局。Go 不承诺字段排列和填充方式，编译器可以调整，布局一变，unsafe 代码静默读错。
- uintptr 与 Pointer 混用。uintptr 不是指针，GC 不认它，把它存着当指针用，对象可能在转换间隙被回收。规矩是转换必须在一个表达式里一次完成。

**避免滥用的规矩**
- 只在边界用。把 unsafe 集中在"线格式字节 ↔ 结构体"那一小处，不让它渗进业务逻辑。
- 能用标准库就别用。encoding/binary 能解就用它，只有确实要零拷贝、要性能时才上 unsafe。
- 不用它做类型转换。要转类型用语言允许的方式。
- 用编译期断言把契约钉死，让编译器帮你守，而不是靠记忆。
- 不长期持有 Pointer 转出的 uintptr。
- 范围越小越好，加注释说明为什么非它不可，方便评审。

**回落到我们项目**
- 我们项目中把 ringbuf 样本转成结构体，属于 unsafe 的正典用法，没问题。配套那对尺寸断言是必须的，因为它把布局契约变成了编译期检查。
- Sizeof 断言只保证总大小，不保证字段没被交换。两个同为 4 字节的字段对调，尺寸不变，断言照样过，但语义错了。要更严，得对关键字段再补 Offsetof 断言，把每个字段的偏移也钉住。

###### memset  |  malloc  |  calloc 的联系和区别
用一句话总结它们的关系：calloc ≈ malloc + memset（清零），但它们在底层细节和适用场景上有着明确的区别

1. **malloc (Memory Allocation)**
    - 特点：只负责分配内存，不管里面有什么。刚分配的内存里可能是上一个程序留下的垃圾数据。
    - 使用场景：如果你打算立刻覆盖这块内存的所有内容，用它最快，因为省去了清零的开销。

2. **calloc (Contiguous Allocation)**
    - 特点：分配内存，并自动把这块内存全部置为 0。
    - 底层：calloc 内部实际上就是先调用 malloc，然后调用 memset 把内存清零。
    - 使用场景：需要初始化状态的数组，比如你上一题拓扑排序里的 indegree（入度数组）和队列。用 calloc 直接分配，里面全是 0，非常省心。

3. **memset (Memory Set)**
    - 特点：它不分配内存，只是对已经分配好的内存进行按字节的填充。
    - 使用场景：用于重置一大块内存（比如重置数组或结构体），或者给字符数组赋值。

memset 是按字节（Byte）操作的，这是最容易踩的坑
- 清零数组
- 给字符数组赋值
- 将数组初始化为 -1
```C
int arr[100];
memset(arr, 0, sizeof(arr)); // 将 arr 的所有字节置为 0，int 的 0 的二进制就是全 0，安全。

char str[100];
memset(str, 'A', sizeof(str)); // 全部变成 'A'

int arr[100];
memset(arr, -1, sizeof(arr)); // 安全的，因为 int 类型的 -1 在二进制里是 0xFFFFFFFF，按字节正好都是 0xFF
```

**错误用法**（极容易引发 BUG）
> 千万不要用 memset 把 int 数组初始化为 0 以外的非 -1 的值！

比如想把数组初始化为 1
```C
int arr[10];
memset(arr, 1, sizeof(arr)); 
// 你认为 arr 变成了 [1, 1, 1...]，实际上变成了 [0x01010101, 0x01010101...]
// 也就是 16843009！因为每个字节都被设成了 0x01。
```
如果需要把 int 数组初始化为 1，只能用循环 for，或者使用 calloc（清零后手动修改）

###### BPF_MAP_TYPE_RINGBUF | BPF_MAP_TYPE_HASH | BPF_MAP_TYPE_PERCPU_ARRAY
**靠什么区分**
三者都靠结构体里那个 __uint(type, ...) 字段，它的值就是 BPF_MAP_TYPE_* 这个枚举。libbpf 读这个字段，把 map_type 传给 bpf()，内核据此建对应的表。
ringbuf 的声明里只有 type 和 max_entries，不写 __type(key/value)；array 和 hash 必须写 key 和 value。但这只是写法差异，真正的判据仍是 type。
类型决定的是行为（环、下标表、还是字典），不负责区分实例。想要几条 ringbuf，就写几个不同变量名的定义，它们就是几条独立的环。不需要为了"区分"去改 type。

```C
struct {
    __uint(type, BPF_MAP_TYPE_RINGBUF);
    __uint(max_entries, 1 << 20);
} a SEC(".maps");

struct {
    __uint(type, BPF_MAP_TYPE_RINGBUF);
    __uint(max_entries, 1 << 20);
} b SEC(".maps");
```

**max_entries 的含义**
- ringbuf：字节数，即那块环形缓冲的总大小，要求是 2 的幂、按页对齐。它既不按键也不存条目，读写走 reserve/submit/discard，不走 lookup/update。
- percpu array 和 array：元素个数，键就是 0 到 max_entries-1 的下标。全部预分配，即使没写过也在。
- hash：最多能容纳的条目数，是容量上限，不是固定长度。按需分配，可增可删，实际占用小于等于它。

**联系与区别**
- 存储模型不同：ringbuf 是字节流，不按键；array 是定长下标表；hash 是稀疏键字典。
- 访问接口不同：ringbuf 用 reserve/submit/discard；array 和 hash 用 lookup/update/delete，其中 array 不能 delete。
- 并发模型不同：percpu 系列每个 CPU 各一份，写是普通加法，不要原子；array 和 hash 是全体共享一份，多 CPU 同时写需要原子操作或锁。
- 内存形态不同：array 预分配满额，hash 按需增长，ringbuf 是固定一块环。

**各自适合什么**
- ringbuf：逐条事件流，长度可变，讲究顺序，丢一点也不至于失真，比如慢调用事件、异常事件。
- percpu array：键是小而密的整数，做计数最合适，比如按 syscall id、按 errno 计数，就是你现在这两张。
- hash：键稀疏或值域巨大，或需要删除键，比如按 pid、pid_tgid、元组索引，或要存起止时间这类用完就删的临时项。

**常见滥用**
- 用 ringbuf 做统计：高频逐条送，既刷屏，环满时还丢，聚合意义全毁。统计应该走计数 map。
- 用 hash 存小而密的整数键：浪费且慢，该用 array。
- 用 percpu array 存 pid 这种大值域键：键越界，lookup 拿不到，等于没存。
- 读 percpu map 只读一个 CPU 的槽：忘了跨 CPU 求和，数字会偏小。
- hash 只写不删：键无限累积，内存和遍历成本一起涨，尤其是按 pid 建的。
- 共享 map 不加原子就自增：并发下计数偏小，percpu 就是为了躲开这件事。
