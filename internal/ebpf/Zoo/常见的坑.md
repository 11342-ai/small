**出现问题**:
未能放开 memlock rlimit（新内核可忽略）: failed to set memlock rlimit: operation not permitted

**错误分析**
说明程序编译时停留在那个map create，因为程序中有 const pid_t pid_filter，落在.rodata 段，加载时cilium/ebpf 要先按这段说明建一张 rodata map，再 load 程序——建 map 就是第一个 bpf() 调用，所以报错停在这里，连程序本身都没有送进verifier
rlimit.RemoveMemlock这个情况可以排除。一是内核 7.0 早已把 BPF 内存改成 memcg 记账，不再吃 memlock rlimit；二是我们代码里本来就调了 rlimit.RemoveMemlock()

###### id / tid / tgid
```C
u64 id = bpf_get_current_pid_tgid();
u32 tid = (u32)id;      /* 低 32 位 */
u32 tgid = id >> 32;    /* 高 32 位 */
```
注意 helper 的名字有点反直觉：叫 pid_tgid ，但低 32 位是 task_struct->pid ，高 32 位才是 tgid。

内核视角: 
- task_struct->pid是tid（线程号）
- tgid是线程组的ID,也就是用户态说的进程号
- 单线程时两个相等，所以平常感觉不到

- pf_get_current_pid_tgid() 返回 u64：高 32 位 tgid，低 32 位 pid。
- 示例里常把它命名成 id，忘了 >>32 拿到的就是 tid
- sched_process_fork 的 ctx->parent_pid / child_pid 都是 tid（task_pid_nr）
- fork 的是调用 fork 的那个线程
- clone 出线程时子任务 tid≠tgid，且子tgid 等于父 tgid。

- ps 默认列的是 tgid（进程）
- ps -eLf / -T 的 LWP/SPID 才是 tid
- /proc/<pid> 是 tgid
- /proc/<pid>/task/<tid> 是线程
- getpid() 给 tgid，gettid() 给 tid。

- uid ：身份权限的编号，他说的是以谁的权限在跑
- uid空间是用户帐号

```C
u64 id   = bpf_get_current_pid_tgid();
u32 tgid = id >> 32;      /* 便宜、常用 */
u32 tid  = (u32)id;

struct task_struct *t = (struct task_struct *)bpf_get_current_task();
u32 tgid2 = BPF_CORE_READ(t, tgid);       /* 语义最直白，多一次解引用 */
u32 tid2  = BPF_CORE_READ(t, pid);
```

###### 常见的坑
bpf_get_current_task() 返回的是标量,强转成 struct task_struct * 之后直接 task->parent->pid ,verifier 不认(报 invalid mem access)

常见的解决方法: 走CO-RE
```c
// 原先错误解法
struct task_struct *task = (struct task_struct *) bpf_get_current_task();
e = bpf_ringbuf_reserve(&process_observation, sizeof(*e), 0);
e->parent_pid = task->parent->pid;

// 正确的写法
e->parent_pid = BPF_CORE_READ(task, real_parent, pid);
```

另外的坑
这个示例中那个task有parent和real_parent,它们有一定区别
- real_parent = 真正生下它的那个进程,不受调试影响。
- parent = 当前父,会被 ptrace 改写 —— 用 gdb/strace attach 上去之后,那个进程的 parent 就变成调试器了


###### 常见的坑:字节对齐问题
Go语言侧和C语言的struct内存分配规则有一定区别，如果各个参数没有对好，会出现拿取数据异常的问题
所以，需要一定方法锁定/填充那个内存空洞

###### 常见的错误
Go语言中，某一个 struct (如struct A) 内部有一个 Kind 字段，那么，以它为接受者，不可以有一个 Kind() 的函数

###### verifier拒绝加载
**ctx 指针不能做算术后再解引用或当内存传**
内核不允许对“被算术修改过的ctx指针解引用，也不允许把它当成内存地址传给helper
- ctx是PTR_TO_CTX,只能按照format里的固定偏移直接读字段，一旦做偏移字段的事情，verifier就把它标记为 modifier ctx ptr，后面任何解引用都会被拒绝
- 有时候能够通过，是因为i这个写法处于灰区，能不能通过取决于那个 clang 优化后生成的指令形态
错: bpf_probe_read_kernel_str(dst, n, (void *)ctx + off);
对: BPF_CORE_READ_STR_INTO(&e->child_comm, child, comm);
错点: 把偏移加进 ctx 指针寄存器之后, verifier 记为 modified ctx ptr, 后续解引用全拒。
区分两件事: 
- "读 ctx 的字段"(偏移写在指令立即数里) 永远合法,
- "把偏移加进 ctx 指针"(偏移进了寄存器) 才非法。这条的要点就是这个区别。

**kfunc 拿到的引用, release 之后不能再用**
那个指针释放后，就不能继续引用了，释放后，那个指针就会失效，verifier一定会拦阻，内容一定要在那个 release之前读取
错: child = bpf_task_from_pid(pid); bpf_task_release(child); BPF_CORE_READ(child, comm);
对: if (child) { 先把要读的字段读完; bpf_task_release(child); }
错点: release 后指针悬垂。verifier 在带引用计数跟踪的路径上通常会拦,
     但不要依赖它兜底——不被跟踪的裸指针漏过去就是运行期读脏数据。

**同一个 ctx 字段读多次, clang 可能把 ctx+off 提到寄存器**
在内核中，同一个ctx字段在被读了多次的时候，有时候那个 clang 为了图省事把一个地址提取到寄存器中，会导致那个内存偏移；而verifier只认一种形态--基寄存器保持原样、偏移写在指令的立即数里。一旦偏移被加进寄存器，它就会判断用户修改了ctx指针
错: e->a = ctx->child_pid; ... ctx->child_pid; ... ctx->child_pid;
对: __kernel_pid_t child_tid = ctx->child_pid; 之后只用 child_tid
错点: verifier 只认"基址寄存器 + 立即数偏移"的直接读。
状态: 待确认。目前是从报错反推(off=20 正是 child_pid 的偏移, 寄存器由 R2 变 R7),
     完整日志没看过。同一写法能否通过取决于 codegen, 属灰区。

排查: cilium/ebpf 默认把日志省略成 "(N line(s) omitted)"。
     fail("%v", err) 看不到关键行, 换 fail("%+v", err),
     或给 ebpf.ProgramOptions 设 LogLevel: ebpf.LogLevelInstruction 并放大 LogSizeStart。

规避: 需要读任务字段的观测点优先用 raw tracepoint——args 直接是 task 指针,
     无 data_loc、无 ctx 字段读取, 上面三类一次全躲过。

###### tracepoint | raw
- 两者都是可以挂载在同一个内核hook点，也就是它们调用的是同一个trace点，所以触发时机、频率、次数完全一致
- 两者也不互斥，可以同时挂载多个程序

- tarcepoint走的是那个 BPF_PROG_TYPE_TRACEPOINT ，通过 perf_event_open 挂到tracefs里那个tracepoint的id; 内核先把参数打包到那个特定 struct 的 ctx 中计算偏移，程序再从这个ctx读，comm这种变长字段还要靠 __data_loc_child_comm算偏移
- raw_tracepoint/sched_process_fork 走的是 BPF_PROG_TYPE_RAW_TRACEPOINT ，通过 bpf(BPF_RAW_TRACEPOINT_OPEN) 直接挂上去，跳过 perf 和格式化，参数就是 TP_PROTO 的原始参数

- raw 的好处：没有格式化开销；参数是真正类型化的指针，verifier 心里有数；有时可以省去那个查找等的复杂度和开销
- tracepoint 的好处：字段名是内核承诺的 ABI， format 文件就是契约，跨版本稳；工具链友好，tracefs 里能直接看 format，trace-cmd 也能读；不依赖任何 kfunc

- raw 的代价： args 的顺序和类型由 TP_PROTO 决定，内核改签名你就得跟着改，没有 format 那份"文档"可对照；要求内核 4.17 以上
- bpftrace 里还得自己转型。tracepoint 的代价：只有 format 里那几个字段，想要 child 的 tgid 就得额外查一次，而且每加一个字段都要等内核改 format。
